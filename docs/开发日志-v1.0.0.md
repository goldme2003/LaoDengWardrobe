1. 首先按 2026-11-10 条目 3 的历史方案核对：`fsutil behavior query disablelastaccess` = 1（历史修复仍在生效）、发现并终止了僵尸双 MCP 实例（PID 19220 / 28432 同命令行并发管理同一 `.miniapp`，与 11-10 EPERM 现象一致）——但 hashing 仍稳定失败，说明另有主因。

### 1. 新增「版本一致性校验」开发前置规范（写入 AGENTS.md）

**版本**：v0.7.0（开发版）
**修改时间**：2026-11-11 +08:00

**背景**：用户要求后续所有开发动作前必须先做版本一致性校验：拉取远端分支元数据 → 对比本地版本与 GitHub 主线（提交时间 + 版本号）→ 若远端为最新则同步覆盖本地。经确认，口径调整为「`main` + `untested` 双基准 + 安全同步 + **保留高版本**」。

**口径调整原因**：本仓库 `origin/main` 为「文档基线 + 版本快照」分支（由 `untested` 合入生成），校验时实测 `origin/main` 最新快照为 **v0.6.0**（`e282e1f`，2026-11-09），而本地 `untested` 已是 **v0.7.0**（`ea48a90`）。若按原文「校验通过即用 main 完全覆盖本地」，会在快照落后时把工作区降级并丢弃未提交改动。故确立**保留高版本**原则：版本号高者为准，远端低于本地时不拉取、不降级、不覆盖。

**本次变更**：

#### 问题 4：直连 github.com 失败，经本地代理推送成功

- **现象**：`git push` 两次失败，无法直连 GitHub。
- **错误代码 / 内容**：

```text
fatal: unable to access 'https://github.com/goldme2003/LaoDengWardrobe.git/': Recv failure: Connection was reset
（退出码：128）
```
