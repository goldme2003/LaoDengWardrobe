## 2. 腾讯位置服务开通与配置步骤（A 阶段前置）

### 2.1 账号与认证

1. 浏览器打开腾讯位置服务控制台 <https://lbs.qq.com/dev/console/application/mine>，使用**微信扫码**登录（推荐，便于与小程序主体对齐）。
2. 进入「控制台 → 账号中心 → 实名认证」，选择主体类型：
   - 个人：身份证 + 人脸核身；企业：营业执照 + 对公打款/法人认证。
   - 未实名无法创建 Key 与调用 WebServiceAPI。
3. 认证审核通过后，在「配额管理」确认免费额度（个人认证逆地址解析通常为 5000 次/日、QPS 5，**以控制台实际显示为准**）。

### 2.2 创建应用与 Key

1. 「控制台 → 应用管理 → 创建应用」，名称填 `老登衣柜`，类型选「微信小程序」。
2. 在应用下「添加 Key」，配置：
   - Key 名称：`laodeng-wardrobe-prod`
   - 启用产品：**WebServiceAPI**（逆地址解析 `geocoder`、地点搜索 `place`）
   - 绑定小程序 AppID：`wxe42fe1ecc2645be1`
   - 安全设置：填写服务器域名白名单（本项目走云函数调用，可不填；若后续前端直连需填 `apis.map.qq.com`），并妥善保存 **SK**（签名密钥，仅云函数使用）
3. 记录三项配置，写入云函数环境变量（**不写入前端、不提交仓库**）：

| 变量名 | 值来源 | 使用位置 |
| --- | --- | --- |
| `TENCENT_MAP_KEY` | 控制台 Key 列表 | `cloudfunctions/weatherProxy`（逆地理） |
| `TENCENT_MAP_SK` | Key 详情页（可选，仅签名校验时用） | 同上 |
| `QWEATHER_KEY` | 和风天气控制台 | 同上（天气数据） |

### 2.3 小程序侧域名与权限

1. 微信公众平台 →「开发管理 → 开发设置 → 服务器域名 → request 合法域名」：
   - 走云函数代理时**无需**添加（云函数不受域名限制），推荐此方式；
   - 若改为前端直连，需添加 `https://apis.map.qq.com`、`https://devapi.qweather.com`。
2. 「开发管理 → 接口设置」→ 申请「地理位置」接口（`wx.getLocation`），填写使用场景：「根据用户所在城市展示当日天气与穿衣推荐」，提交后等待审核（通常 1–2 个工作日）。
3. 「设置 → 基本设置 → 用户隐私保护指引」→ 勾选并填写「位置信息」用途，否则 2023 年后 `wx.getLocation` 会直接失败（隐私接口新规）。

### 2.5 天气数据源说明（修正 9.4 选型）

腾讯位置服务**只提供定位与逆地理**，不提供天气数据。天气按以下口径落地：

| 用途 | 服务 | 说明 |
| --- | --- | --- |
| 定位 / 逆地理 | 腾讯位置服务 WebServiceAPI | 本文档 2.1–2.4 |
| 天气数据（主） | 和风天气 QWeather | 需 `QWEATHER_KEY`；免费 1000 次/日，实时 + 3 天预报 |
| 天气数据（兜底，**已接入**） | 中国天气网 `d1.weather.com.cn` | 免密钥、实测可用；非官方接口，有变更风险 |
| 天气数据（备） | 腾讯天气（非公开接口） | 不作为正式依赖，仅作参考 |

**接入策略**：`和风（有 Key）→ 中国天气网（免密钥兜底）→ 前端本地模拟数据`，任一层失败自动降级，页面不阻塞。当前无需任何 Key 即可展示真实天气。

**风险与缓解**：中国天气网为非官方页面接口，字段或路径可能变动；已做“解析失败即降级”处理，并保留和风作为主源，Key 配好后无需改代码即可切换。

**注意事项**

1. 免费订阅额度为 1000 次/日，本项目 30 分钟缓存 + 本地缓存可覆盖日常使用；超限时会自动回退中国天气网，不会报错。
2. Key 权限范围：仅用于本项目的天气与城市搜索接口，不要复用其他业务 Key。
3. 若控制台不再提供 `devapi` 公共域名（仅独立 API Host），必须改 `WEATHER_HOST`、`GEO_HOST` 两个常量后再部署。
4. 和风失败时的日志关键字：`QWEATHER_CITY_xxx`（城市检索失败）、`QWEATHER_API_xxx`（预报接口失败）、`QWEATHER_HTTP_4xx`（Key 无效/额度用尽）。

## 3. 功能设计

### 3.1 A 阶段：天气接入（`cloudfunctions/weatherProxy`）

| 项 | 设计 |
| --- | --- |
| 入参 | `{ action: 'city' \| 'weather', city?, lat?, lon? }` |
| 逆地理 | `GET https://apis.map.qq.com/ws/geocoder/v1/?location={lat},{lon}&key=...` → 取 `result.address_component.city` |
| 天气 | 链路：和风（`QWEATHER_KEY`）→ 中国天气网（免密钥）→ 抛错由前端降级 |
| 归一化 | 输出既有 `WeatherInfo`：`{ city, today:{date,cond,low,high}, days[3] }`，现象映射为晴/多云/阴/小雨/中雨/大雨/雪/雾 |
| 缓存 | 云函数实例内存 30 分钟，`key = 城市名`；命中不计费 |
| 限流 | 单用户 1 分钟最多 1 次真实请求 |
| 超时 | `config.json` 声明 `timeout: 20` |

### 3.2 B 阶段：推荐引擎（`src/services/recommend.ts`，纯函数 + 断言测试）✅ 已完成

1. 输入：`WeatherInfo` + 当前衣橱衣物列表（类型、季节、内外穿、材质、适用场合）+ 搭配场景（预设选项）；
2. 天气基准：**取明日预报 `days[0]`**（`weatherProxy` / `mockWeather` 的 `days` 顺序为「明天 / 后天 / 大后天」，v1.4.2 修正了此前误取 `days[1]`（后天）导致基准错位一天的问题）；无明日数据时回退今日并在理由中标注「今日」；
3. 规则：按体感温度均值分档（<5 / 5–15 / 15–22 / 22–28 / >28℃），各档位定义搭配槽位计划（cold 必含外套+上装+下装、cool 必含外套、mild 外套可选、warm/hot 无外套且下装兼容裙装），品类按关键词模糊匹配（类型为用户自定义字符串）；材质按保暖/透气关键词加分，低温档优先保暖材质、高温档优先透气材质，外套槽位优先「外穿」层与喜爱项；
4. 场景维度（v1.4.1）：预设 6 类场景（日常 / 通勤 / 运动 / 正式 / 居家 / 旅行，另含「不限」），与衣物「适用场合」预设一一对应，覆盖日常 80% 以上着装要求；**只允许点选预设，不支持自由输入**；命中 `occasions` +4、命中品类 / 材质 / 名称关键词 +2；衣橱无该场景匹配衣物时自动降级为「不限」，不输出误导性场景理由；
5. 排序：季节匹配（每命中 +3）→ 材质适配（±2）→ 场景匹配（v1.4.1）→ 外穿/喜爱加权 → 同类型取最近新增；
6. 输出：`{ items: ClothingItem[]; reason: string }[]`（最多 3 套，按衣物 id 去重），`reason` 由模板生成（城市+明日温度+现象+场景+档位说明+衣物名+穿搭要点），不调用大模型，保证 ≤2s 与可解释性；
7. 降级：天气不可用 / 衣物为空 / 类型全不匹配 → 返回空数组不展示推荐卡片，不影响原有功能；
8. 展示：`RecommendCard` 组件位于衣柜页筛选栏下方（筛选时隐藏），含场景胶囊标签、横排衣物缩略图 + 理由 +「换一件」（轮换下一套）/「一键采纳到明日穿搭」；选择场景或切换城市后重新生成时展示显性加载态「穿搭建议生成中…」（v1.4.2，两种触发共用同一套加载逻辑）；
9. 实现偏差说明：「近 30 天未穿优先」依赖日记与衣物关联数据，当前 `DiaryEntry` 无衣物引用，暂不参与排序，待日记支持关联衣物后补齐；
10. 验证：esbuild 独立打包断言测试 11/11 通过（明天 days[0] 取值且不误用后天、无明日预报回退今日并标注「今日」、运动场景优先、无匹配场景降级、空天气/空衣橱降级、场景覆盖度）。

### 3.3 C 阶段：空衣橱专属引导（云函数 + 混元）

#### 3.3.1 触发条件

- 当前激活衣橱的衣物数量为 0；
- 衣柜页展示空态时调用（同一衣橱 + 同一性别/年龄 24 小时内只调用一次，命中本地缓存直接展示）；
- 网络失败/模型失败 → 展示内置兜底文案，不展示错误。

#### 3.3.2 云函数 `emptyGuide`

| 项 | 设计 |
| --- | --- |
| 入参 | `{ action: 'ping' \| 'guide', gender: 'male'\|'female'\|'other', age: number, weather?: { cond?: string, low?: number, high?: number } }`（v1.4.0 新增 `weather`） |
| 上下文 | 必传 `gender`、`age`（取自「我的」页个人资料，随衣橱主人联动）；缺参返回 `BAD_PARAM`；`weather` 可选，由前端在天气加载完成后传入（天气失败时缺省，走无天气流程） |
| 提示词 | 单条 user 消息（无 system 消息，精简 token）：`穿搭顾问。{性别}，{年龄}岁，衣橱为空。天气{low}~{high}℃ {cond}。给1条≤50字的入门单品建议，侧重{年龄风格}。只输出JSON：{"tips":["建议"]}`；年龄风格：<18 校园、18–30 通勤/休闲、31–50 通勤/质感、>50 舒适/保暖；无天气时省略天气句 |
| 输出 | `{ code:'OK', tips: string[]（1 条）, source:'hunyuan'\|'fallback', weatherUsed: boolean }` |
| 缓存 | 云函数实例内存：模型结果 24 小时、兜底结果 10 分钟；前端本地存储 24 小时，`key = gender + age + 天气签名`（签名 = 现象 + 温度档位：<5/5–15/15–22/22–28/>28℃，不新增数据库集合） |
| 降级 | 模型请求 25s 绝对硬超时（超时即销毁请求，确保函数在平台 60s 上限前返回）；模型超时/鉴权失败/解析失败 → 返回按年龄性别挑选的内置文案 + 温度档位提示（`source:'fallback'`，`code:'OK'`），前端无感 |
| 复用 | 复用 `recognizeClothing` 的混元 provider 与熔断/计数逻辑，避免重复封装 |

#### 3.3.3 前端展示

- 衣柜页空态区域：标题「这个衣橱还空着」+ 1 条动态建议（≤50 字）+ 次级引导提示（「添加自有衣物后，可按你的身材与当前天气获取更精准的个性化推荐」）+「添加衣物」按钮；
- 文案展示在空态描述行，超长自动省略；等待天气首次加载完成（成功或失败）后才请求建议，避免无天气文案二次刷新；加载中保持默认文案，不阻塞添加操作；
- 埋点：`empty_guide_show` / `empty_guide_fallback` / `empty_guide_click_add`。

### 3.4 D 阶段：明日穿搭衔接 ✅ 已完成

- 衣橱为空：走 C 阶段天气适配引导流程（空态文案 + 添加衣物引导），与 D 无关；
- 衣橱非空：推荐卡片「一键采纳」批量写入当前衣橱 `tomorrowOutfits` 勾选数据（store 新增 `adoptTomorrowItems`，已勾选自动跳过，单次 commit）；「换一件」在 1–3 套间轮换并重置采纳态（全部勾选完成时按钮置灰「已采纳 ✓」）；
- 明日穿搭页原有手动勾选逻辑不变，两类入口共用同一份数据结构，未新增字段。

## 4. 异常捕获与降级矩阵

| 场景 | 处理 | 用户可见 |
| --- | --- | --- |
| 定位授权拒绝 | 回退城市选择 | 正常展示所选城市天气 |
| 逆地理失败 | 使用上次城市缓存 → 默认城市 | 天气照常展示 |
| 天气接口失败/超限 | 云端旧快照 → 本地缓存 → 隐藏天气 | 不阻塞衣橱 |
| 云函数未部署/超时 | 前端 20s 硬超时 + 明确提示 | 提示「天气暂不可用」 |
| 混元 Key 缺失/超时 | 内置文案兜底 | 文案正常，无报错 |
| 性别/年龄缺失 | 使用默认值（other / 30）并记录告警 | 文案正常 |

## 5. 验收标准

1. 已授权定位：进入衣柜页 ≤3s 展示真实城市与真实天气；与官方天气对比温度误差 ≤2℃。
2. 未配置任何 Key：仍展示真实天气（来源 `weather.com.cn`），返回含 `source` 字段。
2. 拒绝定位：可通过城市列表切换，切换后数据正确刷新，无重复授权弹窗。
3. 空衣橱：展示 1 条（≤50 字）含性别/年龄上下文的建议，且不同年龄段文案存在可辨识差异；模型故障时仍有兜底文案（`source: fallback`）。
4. 天气或模型任一侧故障时，衣橱主流程无报错、无白屏、无阻塞。
5. 缓存命中率 ≥90%（同城市 30 分钟内重复进入不重复计费）。
6. 全部用例纳入 `docs/测试方案-v1.3.0.md` 执行并留档。
