## 1. 背景与目标

个人及家庭成员的衣物照片、类型、颜色、材质、季节属性分散在记忆和相册中，用户在穿搭决策（如「今天降温，找一件深色的冬季外套」）时无法快速定位衣物，也难以了解自己与家人各拥有什么。

老登衣柜是一个面向个人的衣物管理微信小程序：用户可以为多位家庭成员分别建立衣橱，通过拍照组快速记录衣物，为衣物标注服装类型、内外穿、颜色、材质、季节等属性与备注；并可以按这些维度浏览、筛选，结合内嵌天气预报辅助当日穿搭选择。

**可观察的产品结果**：用户在 1–2 分钟内可以完成一件衣物的拍照录入（照片组 + 属性选择）；录入后，用户可以按服装类型、颜色、材质、季节、喜爱任一维度筛选某位用户的衣物并查看详情；首页可以看到当日天气，作为穿搭参考。

## 3. 产品模型

### 3.1 核心对象

**衣橱（Wardrobe）**：一位用户的独立衣物集合。

| 字段 | 说明 |
| --- | --- |
| 用户名称 | 衣橱标识（衣橱主人称呼，如「老登」），创建后可修改（命名规则 v0.7.0 起不含用户名，修改不影响已有衣物名称） |
| 主题色 | 新建衣橱时从预设色板（8 色）中选定，用于区分不同人的衣橱；切换衣橱时衣柜页主题色随之变化 |
| 创建时间 | 系统记录 |
| 衣物条目 | 隶属于该衣橱的衣物列表 |

**衣物条目（Item）**：隶属于某个衣橱的单件衣物。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 照片组 | 图片 1–9 张 | 是 | 第 1 张为列表展示主图；来源为拍摄或相册 |
| 名称 | 文本 | 自动 | 系统按「用户-服装类型-编号」自动生成（见 6.2），允许用户修改 |
| 服装类型 | 单选 | 是 | 预设项 + 自定义项（见 6.1），如上装、裤装 |
| 内外穿 | 单选 | 是 | 内穿 / 外穿（固定枚举） |
| 颜色 | 单选 | 是 | 预设项 + 自定义项 |
| 材质 | 单选 | 是 | 预设项 + 自定义项 |
| 季节 | 多选（1–4 项） | 是 | 春 / 夏 / 秋 / 冬（固定枚举） |
| 尺码 | 单选 | 否 | 预设 XS/S/M/L/XL/XXL（固定枚举），可留空 |
| 品牌 | 文本 ≤20 字 | 否 | 常用品牌预设点选 + 手动输入，输入时联想提示匹配的常用品牌，也可输入预设外品牌 |
| 适用场合 | 多选 | 否 | 预设：日常/通勤/运动/正式/居家/旅行（固定枚举），可留空 |
| 喜爱 | 布尔 | 否 | 默认「否」，用户可随时切换 |
| 备注 | 多行文本 ≤200 字 | 否 | 清洗方法、衣物来源、购买渠道等 |
| 录入时间 | 系统记录 | — | 用户不可编辑 |

- 除照片组外的必填属性（服装类型、内外穿、颜色、材质、季节）在保存时校验：任一为空则无法保存，并高亮提示对应字段。
- 列表按录入时间倒序展示。

### 3.2 状态

- **衣橱**：正常 / 已删除。删除衣橱连带删除其下全部衣物（见 FR-01）。
- **衣物条目**：正常 / 已删除。已删除条目不出现于任何列表与筛选结果；MVP 无回收站，删除即最终生效（删除前确认见 FR-08）。

## 4. 核心流程

```text
【衣橱】首次打开 → 自动创建「我的」衣橱 → 可新建其他衣橱（家人/他人）并随时切换

【录入】在当前衣橱下点击"添加衣物" → 拍照/相册选择获得 1–9 张照片
        → 依次选择 服装类型/内外穿/颜色/材质/季节（均必填，可新增自定义选项）
        → 填写备注（可跳过）→ 保存 → 系统自动命名，新衣物置顶

【查看】浏览当前衣橱列表（全部 或 按类型/颜色/材质/季节/喜爱筛选）
        → 点击衣物 → 查看照片组与属性详情 → 喜爱/编辑/删除

【天气】进入首页 → 自动展示当前城市今日及未来 3 日天气 → 穿搭参考
```

## 5. 功能需求

### FR-01 衣橱管理

**目的**：为不同的人（自己、家人、他人）分别管理衣物，互不混淆。

**触发**：进入小程序首页；点击首页顶部的衣橱切换器。

**处理规则**：

1. 首次使用自动创建默认衣橱，用户名称为「我的」。
2. **新建衣橱**：在衣橱管理页输入用户名称（≤10 字，不可与现有衣橱重名），并从预设色板中选择主题色后创建；创建成功后自动切换到新衣橱。
3. **切换衣橱**：通过底部标签页「衣橱」或衣柜页顶部衣橱切换器选择；切换后列表、筛选、添加衣物均针对所选衣橱，衣柜页主题色切换为该衣橱的主题色。
4. **删除衣橱**：在衣橱管理页删除；弹窗确认「将同时删除该衣橱下全部衣物，不可恢复」；确认后连带删除其下全部衣物与照片数据。至少保留 1 个衣橱，最后一个衣橱不可删除。
5. 衣橱名称（主人称呼）可在「我的」页修改；命名规则已不含用户名（见 6.2），修改不影响已有衣物名称。
6. **主题设置入口**：衣橱风格主题在衣橱管理页设置（列表项内提供主题更换入口）；「我的」页不再提供主题设置。
7. **快速切换**：在衣柜页再次点击底部「衣柜」标签时，弹出衣橱选择弹层，可快速切换衣橱（替代长按交互，兼容微信原生 tabBar）。
8. **入口**：衣橱管理为底部标签页（衣柜 / 备选 / 日记 / 我的），「我的」页仅保留指向衣橱管理页的跳转入口，不再承载衣橱管理操作。

**例外**：输入重名或超长时，即时提示并阻止创建。

### FR-02 照片组录入

**目的**：用一组照片完整记录一件衣物（整体、细节、标签等）。

**触发**：在当前衣橱下点击「添加衣物」。

**处理规则**：

1. **拍照**：调起微信相机，每次拍摄 1 张并加入照片组；可连续拍摄多张。
2. **相册选择**：调起微信相册选择器，单次最多选择「9 − 已选张数」张。
3. 照片组总数上限 9 张；达到上限后隐藏添加入口并提示。
4. 获得至少 1 张照片后进入属性编辑页（FR-03）；照片组展示于编辑页顶部，第 1 张为主图。
5. 编辑页提供「设为主图」：将组内任一照片设为主图（与其余照片交换位置）。
6. 提供删除组内照片入口，剩余至少 1 张；删除到 0 张时返回衣柜页，不产生条目。
7. 照片以小程序可展示的格式与适中分辨率保存（压缩策略为技术实现，不在本文档定义）。

**例外**：

| 场景 | 行为 |
| --- | --- |
| 拒绝相机/相册权限授权 | 展示引导文案，提示去设置页开启授权；提供拍照与相册两种入口重试 |
| 拍摄/选择中途取消 | 未获得任何照片时返回衣柜页，不产生条目 |

### FR-03 衣物属性编辑

**目的**：通过标准化控件为衣物建立可筛选的属性档案。

**触发**：FR-02 照片组获取成功后（新录入）；或在详情页点击「编辑」。

**处理规则**：

1. 编辑页顶部为照片组（见 FR-02 第 5–6 条）。
2. 属性控件（单选采用转盘选择 Picker，多选采用勾选；颜色采用色块点选以便直观比对）：

| 字段 | 控件 | 选项来源 |
| --- | --- | --- |
| 服装类型 | 转盘单选 | 预设 + 自定义 |
| 内外穿 | 转盘单选 | 固定：内穿 / 外穿 |
| 颜色 | 色块点选 | 预设 + 自定义 |
| 材质 | 转盘单选 | 预设 + 自定义 |
| 季节 | 勾选多选（1–4 项） | 固定：春 / 夏 / 秋 / 冬 |
| 尺码 | 转盘单选（选填） | 服装类型为「裤装」时：腰围 24–40（英寸，逐档单数与双数连续档位）；其他类型：XS / S / M / L / XL / XXL |
| 品牌 | 文本输入（选填，≤20 字）：常用品牌预设点选 + 手动输入，输入时联想提示 | 预设 + 自由输入 |
| 适用场合 | 勾选多选（选填） | 固定：日常 / 通勤 / 运动 / 正式 / 居家 / 旅行 |

3. **属性文字大小**：属性标签与选项文字采用加大一号的字号（≥32rpx），保证中老年用户可读性。
4. **自定义选项**：服装类型、颜色、材质三个维度在选项面板底部提供「+ 新增选项」入口；输入文本（服装类型 ≤10 字，颜色 ≤6 字，材质 ≤10 字）确认后立即加入该维度选项列表并默认选中当前衣物（规则见 6.1）。
5. **保存**：五个必填属性全部已选且照片组 ≥1 张时方可保存；未满足时「保存」置灰或点击后高亮缺失字段。保存后返回列表，新条目置顶（按录入时间倒序）。
6. 名称由系统自动生成（见 6.2），编辑页展示名称预览；提供「修改名称」入口，允许用户手动改名（改名只影响该条目，不影响编号分配）。
7. **备注**：多行文本框，≤200 字，可跳过。
8. 编辑已有衣物时，保存覆盖对应字段；照片组可增删、可更换主图。

### FR-04 喜爱标记

**目的**：让用户快速标记并回找心爱衣物。

**处理规则**：

1. 详情页提供「喜爱」开关（心形图标），点击即切换喜爱/取消，即时生效，无需保存确认。
2. 列表条目上直接提供喜爱图标：点击切换；已喜爱条目显示实心心形。
3. 编辑页不提供喜爱开关（避免误改），喜爱仅在列表与详情操作。
4. 切换喜爱不改变条目的录入时间与排序位置。

### FR-05 备注

**目的**：记录结构化属性之外的自由信息。

**处理规则**：

1. 备注为多行自由文本，≤200 字，超出后输入框截断。
2. 内容由用户自行决定，常见用途：清洗方法、衣物来源、购买渠道等；产品不强制格式。
3. 备注在详情页完整展示；列表不展示备注。
4. 可留空；留空时详情页显示「未填写」。

### FR-06 衣柜列表与分类筛选

**目的**：在当前衣橱内按维度快速找到衣物。

**触发**：进入小程序首页（衣柜页），或操作筛选器。

**处理规则**：

1. **列表（手风琴分组，v0.7.0）**：当前衣橱全部衣物按服装类型分组，以手风琴折叠面板展示；组头为「类型名 + 件数」，组内衣物按录入时间倒序、条目呈现「主图缩略 + 名称 + 喜爱图标 + 关键属性标签（颜色/季节）」；分组顺序 = 预设类型顺序 + 自定义类型排后。
2. **手风琴展开规则**：默认全部展开；页面向上滚动到底部时自动收起全部分组、向下滑动（回滚）时自动展开；组头可点击手动展开/收起。
3. **筛选维度**：颜色、材质（单选，含「全部」与「未设置」）、穿着季节（多选并集，含「全部」与「未设置」）、喜爱（「只看喜爱」开关）；「服装类型」不再作为筛选项（类型即分组，见第 1 条）。
4. **筛选态列表**：应用任一筛选后，列表退化为平铺网格（不再分组），按录入时间倒序；清除全部筛选后恢复分组展示。
5. 多维度叠加取交集；任一维度选「全部」表示该维度不限制。
6. 选项列表 = 预设项 + 已生效的自定义项（见 6.1）。
7. **空结果**：展示空态文案与「添加衣物」入口。
8. **空衣橱**：当前衣橱无衣物时展示引导页与「添加衣物」主按钮。
9. 顶部展示衣橱切换器与「添加衣物」按钮；天气卡片位于列表上方（见 FR-09）。

**例外**：自定义选项较多时选项面板支持纵向滚动，不设数量上限。

### FR-07 衣物详情查看

**目的**：查看单件衣物的完整信息。

**触发**：在列表中点击任一衣物条目。

**处理规则**：

1. 展示照片组（可左右滑动浏览，主图居首）与全部属性：名称、服装类型、内外穿、颜色、材质、季节，以及选填属性（尺码、品牌、适用场合，未填写不展示）、备注、录入时间。
2. 备注为空显示「未填写」；其余必填属性不会为空。
3. 提供操作入口：喜爱（FR-04）、编辑（FR-03）、删除（FR-08）。

### FR-08 衣物删除

**目的**：移除不再拥有的衣物。

**触发**：在详情页点击「删除」。

**处理规则**：

1. 弹窗确认：「删除后不可恢复，确定删除该衣物吗？」，提供「取消」与「删除」。
2. 确认后条目立即从所有列表与筛选结果中移除，并从本地存储清除照片与属性数据；该条目的编号不回收、不重排（见 6.2）。
3. 取消则无任何变更。

### FR-09 天气预报

**目的**：在衣柜场景内直接获取天气信息，辅助当日穿搭决策。

**触发**：进入小程序首页时自动加载。

**处理规则**：

1. 首页列表上方展示天气卡片，内容包含：城市名、今日天气现象、今日气温范围（最低–最高）、未来 3 日逐日简报（日期、天气现象、气温范围）；今日天气现象与未来 3 日逐日简报均配天气现象图标（晴/多云/阴/雨/雪/雾/雷等，以图标 + 文字呈现）。
2. 位置来源：请求微信定位授权，取当前城市；用户拒绝授权或定位失败时，提供手动选择城市入口（省/市选择），所选城市被记住，后续不再重复请求定位。
3. 天气卡片提供手动刷新；进入首页时自动刷新一次，刷新间隔不限频。
4. 天气信息仅为展示与参考，不参与任何筛选、推荐逻辑。
5. **主题联动（v0.7.0）**：天气卡片配色跟随当前衣橱风格主题——卡片底色/强调色/天气图标点缀色随主题整体联动，不再使用固定配色。
6. **城市覆盖（v1.5.6 登记，未实现）**：当前仅对已收录城市（55 城）返回天气，未收录城市无法展示天气。覆盖不足问题与改造要求见 10.1（R-1）。

**例外**：

| 场景 | 行为 |
| --- | --- |
| 天气数据获取失败 | 卡片展示「天气获取失败」与重试按钮，不影响衣柜功能使用 |
| 定位授权被拒绝 | 提示可手动选择城市；不重复弹授权 |
| 天气服务不可用 | 同「获取失败」处理 |
| 所选城市暂无天气数据（v1.5.6 目标行为） | 明确提示「该城市天气暂未覆盖」，并提供一键切换临近已覆盖城市；真实环境不得以模拟数据冒充真实天气（模拟数据仅限开发/预览环境），不影响衣柜功能使用 |

## 6. 共享规则与例外

**自定义规则（服装类型、颜色、材质适用）：**

1. 在对应维度选项面板底部提供「+ 新增选项」入口。
2. 输入文本确认后立即加入该维度选项列表，并在当前衣物的编辑中默认选中。

### 6.2 命名规则

1. 衣物名称由系统按 **「服装类型-编号」** 自动生成，例如「上装-007」（v0.7.0 起不再包含用户名前缀；历史数据中的旧名称保持不变）。
2. **服装类型** = 该衣物当前的服装类型属性值；编辑修改服装类型时，名称中的类型随之更新（若用户未手动改名）。
3. **编号** = 同一衣橱内同一服装类型下的 3 位流水号（001 起，按录入顺序递增）；删除衣物后编号不回收、不重排。
4. 用户可在编辑页手动修改名称；改名后系统不再自动更新该条目名称，名称与编号的对应关系以名称文本为准。

### 6.3 存储规则（先本地后云端）

1. MVP 阶段所有数据（衣橱、衣物、照片组、属性、喜爱、备注）保存在用户设备本地，无需登录即可使用。
2. 多衣橱数据均存于本地，互不共享。
3. 数据结构与存储访问层的设计需保证：后续版本引入微信登录与云端存储时，可在不改变用户可见行为的前提下替换存储实现；本版不实现任何登录、同步界面或网络请求（天气数据获取除外）。
4. 卸载小程序或清除小程序数据会导致本地数据丢失；MVP 在「关于」页展示一次性数据提示文案，不提供导出功能。
5. **（v1.5.6 登记）** 用户已提出云同步需求（见 10.5 R-5）。在该需求落地前，本节第 1–4 条继续有效；落地时按 R-5 的「本地优先 + 增量同步 + 冲突保留」策略改造存储层，本节相应条款同步修订。

### 6.4 权限

MVP 为单设备个人工具，无角色区分；仅使用微信小程序运行时要求的设备权限：相机、相册、定位（用于天气，见 FR-09）。**（v1.5.6 登记）** 后续规划会员版/普通版两级**能力**区分（见 10.6 R-6），属功能权益差异，不改变数据归属与角色权限模型。

## 9. 智能化扩展功能规划（2026-11-11 用户提出）

> 本章为智能化扩展功能的独立规划章节，三项功能均属后续版本迭代范围（非 v0.7.0 当前交付项），经评审确认后排期开发。

### 9.1 基于实时天气的衣物智能推荐

**功能概述**：结合用户所在地区的实时天气（气温、天气现象、未来数日趋势）与衣物属性（季节、类型、材质），智能推荐当日/次日适合穿着的衣物组合，并说明推荐理由（如「明日降温 8°C，推荐加穿外套」）。

**用户价值**：
- 免去用户每天「看天气 → 想穿什么」的决策负担，缩短出门前的选择时间；
- 降低因天气突变穿衣不当的概率（着凉/中暑）；
- 与现有明日穿搭勾选功能（V6-6）衔接，把「人工勾选」升级为「智能预选 + 人工微调」。

**实现逻辑**：
1. 数据输入：FR-09 天气服务（城市/气温/现象/未来 3 日）+ 衣物档案（季节、类型、内外穿、材质、历史着装日记）；
2. 规则引擎：建立「天气区间 → 适宜穿着组合」映射（如气温 <5°C 推荐羽绒服/厚外套，5–15°C 推荐外套 + 长袖，>28°C 推荐短袖/薄款），叠加用户历史穿着偏好（日记数据）做个性化排序；
3. 推荐输出：在衣柜页「明日穿搭」入口处展示推荐组合卡片，用户可一键采纳或替换单品；
4. 后续可升级：接入云端 LLM/推荐模型（依赖 6.3 云端存储落地），支持更细粒度的材质与体感（风寒指数/湿度）。

**验收标准**：
- 在已授权定位/选择城市且衣物档案非空时，衣柜页能给出 1–3 套推荐组合，且每套附推荐理由文案；
- 推荐组合中的衣物必须属于当前衣橱且季节属性与天气区间匹配（抽检正确率 ≥ 90%）；
- 天气获取失败时优雅降级：不展示推荐或提示手动选择，不阻塞原有功能；
- 推荐生成耗时 ≤ 2s，采纳/替换操作可正常同步到明日穿搭勾选数据。

#### 9.1.1 前置依赖（v1.2.1 补充）

- 定位与逆地理：**腾讯位置服务**（WebServiceAPI），需实名认证、创建 Key、申请 `wx.getLocation` 接口权限并在隐私指引中声明位置用途；
- 天气数据：**和风天气**（主），腾讯位置服务不提供天气数据，9.4 选型已同步修正；
- 完整开通/配置步骤、接口设计、降级矩阵见专项文档 `docs/基于天气的着装推荐-v1.3.0.md`；
- **当前状态：A（天气代理云函数）、C（空衣橱引导）已实施；定位待 `wx.getLocation` 审核通过后接入；B/D 待真实天气数据。**

#### 9.1.2 空衣橱专属引导（v1.2.1 补充）

**功能逻辑**：当当前激活衣橱的衣物数量为 0 时，衣柜页空态展示专属引导建议文案；文案由云函数调用腾讯混元大模型**动态生成**，生成时必须传入当前衣橱主人的**性别、年龄**作为上下文，保证建议与该用户匹配。

| 项 | 规则 |
| --- | --- |
| 触发条件 | 当前衣橱衣物数 = 0，且该衣橱 + 性别 + 年龄组合 24 小时内未生成过（本地缓存命中则不请求） |
| 上下文参数 | `gender`（male/female/other）、`age`（整数），取自「我的」页个人资料并随衣橱主人联动；缺失时用默认值 other/30 并记录告警 |
| 生成约束 | 输出 **1 条**建议，**≤50 字**，具体可执行；按年龄段调整侧重（<18 校园、18–30 通勤/休闲、31–50 质感通勤、>50 舒适保暖） |

### 9.2 基于当季流行趋势的衣物智能推荐

**功能概述**：按当前季节拉取服饰流行趋势（当季流行色、流行款式/材质关键词），与用户衣橱内衣物做匹配，推荐「衣橱里最贴近当季趋势」的穿搭组合，并提示缺失的流行单品（作为购入参考，可与试穿/备选页联动）。

**用户价值**：
- 帮助用户在不添置新衣的前提下穿出当季感，提高衣橱利用率；
- 流行趋势信息个性化呈现，避免用户自行检索筛选的成本；
- 与试穿（备选）页联动形成「缺什么 → 看什么 → 买什么」的闭环。

**实现逻辑**：
1. 趋势数据源：按季节维护趋势关键词库（流行色、款式、材质），MVP 阶段人工更新，后续可接入内容平台/API 自动获取（数据源选型列入开放问题）；
2. 匹配算法：将衣物属性（颜色/类型/材质）与趋势关键词做匹配打分（流行色优先级 > 款式 > 材质），输出 Top-N 单品与组合；
3. 展示位置：「试穿」页顶部增加「当季灵感」卡片位；推荐结果支持一键把缺失单品加入试穿（备选）列表；
4. 冷启动：衣物档案不足时，展示通用当季趋势榜单而非个性化推荐。

**验收标准**：
- 每个自然季节能展示对应趋势内容，且至少给出 3 个基于用户已有衣物的推荐单品/组合；
- 推荐结果中的单品均为当前衣橱真实存在的衣物（颜色/类型可追溯到档案属性）；
- 「加入试穿」操作可正确创建试穿条目并跳转试穿页；
- 无网络或趋势数据拉取失败时不阻塞页面，展示降级文案。

### 9.3 衣物图片识别与属性自动填充

**功能概述**：用户在录入衣物（拍照/相册选图）时，自动识别图片中是否包含衣物及衣物品类（上装/裤装/裙装/鞋履等），识别成功后自动填充服装类型、内外穿、颜色、季节建议等属性字段，用户确认或修正后保存。

**用户价值**：
- 大幅降低录入成本：从「手动选 5+ 个属性」降为「确认/微调 1–2 个属性」；
- 降低录入门槛，提升衣物档案完整度（颜色识别可避免「其他」泛滥）；
- 识别结果即所见，减少属性选错、漏填。

**实现逻辑**：
1. 图片检测：在 add 页/试穿编辑页选图后触发；先做「图中是否含衣物」的二分类判断，无衣物则提示重新拍摄，不做填充；
2. 品类识别：图像分类模型输出服装类型（映射至 6.1 类型预设），置信度低于阈值时仅提示不自动填充；
3. 属性推导：服装类型 → 内外穿默认值；图像主色提取 → 颜色（映射至颜色预设，误差大时置空）；类型 + 当前月份 → 季节多选建议；
4. 交互原则：所有自动填充值均可修改（用户改动后不再覆盖）；识别失败/超时静默跳过，不阻塞手动录入流程；
5. 技术形态：MVP 可用端侧/云开发者工具类图像能力；正式版建议接入云端多模态模型（与 6.3 云端化节奏对齐）。

**验收标准**：
- 上传含衣物的常见品类图片（上装/裤装/裙装/鞋履/配饰）时，品类识别准确率 ≥ 85%，含衣判定误报率 ≤ 5%；
- 识别成功后，服装类型、内外穿、颜色字段自动预填且用户可立即修改，修改结果正确保存；
- 上传非衣物图片（风景/食物等）时不自动填充任何属性，并给出明确提示；
- 识别过程有加载态，失败或超时（≤ 5s）不影响手动录入，无崩溃或卡死。

### 10.1 R-1 天气城市覆盖不全

**问题**：天气仅对本地收录的 55 个城市（`src/data/cities.ts`）返回数据，未收录城市（多数地级市、县级市）无法显示天气，用户「有的城市看不到天气」。

**根因**（2026-11-17 核查代码）：主源和风天气仅在云函数配置 `QWEATHER_KEY` 时启用；未配置 Key 时降级到「中国天气网」链路，而该链路依赖云函数内硬编码的 `CITY_CODE`（55 城），表外城市直接抛 `CN_CITY_UNSUPPORTED`。即**不是和风覆盖不足，而是主源 Key 未配置导致覆盖率退化**。

#### 10.1.1 数据源覆盖量核查（2026-11-17，以官方文档为准）

| 数据源 | 城市覆盖 | 预报能力 | 免费额度 | 结论 |
| --- | --- | --- | --- | --- |

**方案：华风爱科 weathercn.com 为主源 + 和风天气备源 + 高德可选备源 + 编码表离线兜底 + 省市区三级城市选择。**

0. **主源决策（v1.6.0 更新）**：和风天气公共域名 `geoapi.qweather.com` 已 404、`devapi.qweather.com` 2026 年起逐步停止服务，**主源切换为华风爱科 weathercn.com**（中国气象局官方授权，translate + daily API 风格与和风高度相似）。和风天气降为备源（等用户拿到和风控制台分配的独立 API Host 后重新启用）。

1. **主源**：配置华风爱科 `WEATHERCN_KEY`（云端环境变量，不下发前端），城市检索走 `GET /locations/v1/cities/translate?apikey={key}&q={city}&language=zh-cn`，天气走 `GET /forecasts/v1/daily/5day/{locationKey}.json?apikey={key}&language=zh-cn&details=true`。translate 接口直接返回数组，无 code 包装；DailyForecasts 字段映射见 9.4.3。
2. **备源**：和风天气（`QWEATHER_KEY`，等独立 API Host 后重新启用）+ 高德可选备源（默认关闭）。
3. **城市选择**：改为「省 → 市 →（可选）区县」三级选择 + 关键词搜索（汉字/拼音首字母），数据来自华风爱科 translate 接口动态返回；`src/data/cities.ts` 降级为离线兜底（断网/接口失败时可用），并已从 55 城扩至 59 城（新增 4 测试城）。
4. **兜底**：华风爱科 → 和风 → 高德（若启用）→ 中国天气网（编码表内城市）→ 本地缓存 → 明确提示「天气暂不可用」；表外城市提示「该城市天气暂未覆盖」并提供临近城市一键切换，**不得以模拟数据冒充真实天气**。
5. **定位**：`wx.getLocation` 审核通过后，定位坐标经腾讯位置服务逆地理（非华风爱科能力范围）反查城市并自动选中；未通过前维持手动选择。

| 降级链路 | **已实现**：华风爱科（主，`WEATHERCN_KEY`）→ 和风（备，`QWEATHER_KEY`）→ 中国天气网（免密钥兜底，`CITY_CODE` 内城市）；每级失败记录 `console.error` 并继续尝试下一级 |
| 缓存 | 云端内存缓存 30 分钟（key = 城市名），命中不消耗第三方额度；容器内复用 |
| 限流 | 同一用户 1 分钟最多 1 次真实请求（云函数内计数） |
| 错误处理 | 返回 `{ code, message, detail }` 结构；`source` 字段标记实际数据源（`weathercn-pro` / `qweather` / `weather.com.cn`）|
| 备源适配 | 和风天气 `fetchFromQWeather()` 已保留，等独立 API Host 后更新 `QWEATHER_GEO_HOST` / `QWEATHER_HOST`；高德适配层暂未实现 |

**前端改造**

1. 城市选择弹层：由「拼音分组单列」改为「省份列表 → 城市列表 → 区县（可选）」+ 顶部搜索框；保留最近使用城市与当前城市高亮。
2. 搜索：输入 ≥1 个汉字或拼音首字母触发 `citySearch`（防抖 300ms），结果项展示「省 / 市 / 区」层级，避免同名城市误选。
3. 未覆盖城市：卡片展示「该城市天气暂未覆盖」+「切换到 XX（临近城市）」按钮。
4. 离线：接口失败时回退 `src/data/cities.ts` 兜底表（扩至地级市），保证仍可选择主要城市。

**配置与合规**

- 和风 Key 仅存云函数环境变量；小程序隐私指引无需新增声明（城市名为非个人信息，定位另按 9.4.6 处理）。

### 10.2 R-2 出差衣物推荐

**功能概述**：用户输入出差目的地城市与出差天数，系统结合目的地天气与当前衣橱，生成「携带衣物打包清单」与「逐日穿搭建议」，解决出差前挑衣与带几件的问题。

**入口**：衣柜页天气卡片区域新增「出差」入口（会员能力，见 R-6）；进入独立「出差计划」页。

**输入项**：

| 项 | 必填 | 说明 |
| --- | --- | --- |
| 目的地城市 | 是 | 复用 R-1 城市选择（省 → 市），可与当前城市不同 |
| 出发日期 / 返程日期 | 是 | 或直接填写天数 1–14 天；超 14 天提示分段规划 |
| 出差场景 | 是 | 商务正装 / 商务休闲 / 休闲（映射现有场景预设：正式 / 通勤 / 日常） |
| 洗衣条件 | 否 | 有洗衣条件（换洗周期 3 天）/ 无（默认 2 天） |
| 衣物范围 | 否 | 默认当前衣橱；支持指定一人衣橱（多衣橱场景） |

**输出项**：

1. **打包清单**：按品类分组（外套 / 上装 / 下装 / 内衣 / 鞋履 / 配饰），每组列出建议件数与具体衣物（主图 + 名称），并可勾选「已打包」。
2. **件数规则**：可换洗品类件数 = ⌈天数 ÷ 换洗周期⌉（默认周期 2 天，有洗衣条件 3 天）；内衣袜子 = 天数；外套、鞋履各 1–2 件（按温差跨度决定）；同日复用已打包单品不重复计数。
3. **逐日穿搭**：每天 1 套（含理由：目的地当日天气 + 场景），前 3 天用真实预报，第 4 天起用「近期温度区间估计」并标注「预估」。
4. **缺件提示**：衣橱内不满足当前场景/天气的关键品类（如缺正装鞋、缺外套）给出提示，可一键加入试穿（备选）列表。
5. **保存与复用**：出差计划可保存、可重命名、可删除；离开页面后再次进入可继续。

**与现有能力的关系**：复用 `weatherProxy`（目的地天气）、`outfitRecommend` / 本地规则引擎（按目的地天气而非本地天气生成搭配）；新增「出差」场景预设与多日计划数据结构。

**降级**：目的地天气失败 → 使用本地规则引擎 + 温差提示，标注「目的地天气暂不可用」；衣橱为空 → 引导添加衣物，不生成清单。

**验收标准**：

- 7 天出差（无洗衣条件）清单中上装/下装件数 = 4（⌈7÷2⌉），内衣 7 件，与规则一致；
- 逐日穿搭每天 1 套，季节与目的地温度匹配，前 3 天使用真实预报；
- 缺件提示可正确加入试穿列表；
- 生成耗时 ≤5s（本地规则），AI 增强不走阻塞主流程（与 R-3 一致）。

**涉及范围**：新增出差计划页与数据结构、推荐引擎（目的地城市入参）、天气服务、衣柜页入口、store、试穿页联动。

### 10.3 R-3 推荐性能优化

**问题（实测）**：点击场景或进入首页后推荐常需 30 秒–1 分钟；前端调用 `outfitRecommend` 时无客户端超时，云函数 `timeout` 为 60s，混元返回慢即整卡等待。

**需求规则**：

1. **本地优先渲染**：进入首页立即用本地规则引擎生成结果（目标 ≤300ms，首屏 ≤1s 可见），UI 先行展示；AI 结果返回后原地替换，保留「混元生成」角标以区分来源。
2. **客户端硬超时**：AI 请求硬超时 **≤8s**（建议 8s），超时保留本地结果，不弹错误、不阻塞操作；「换一件」在本地候选间轮换，不重新发起 AI 请求。
3. **服务端提速**：精简入参（衣物上限 20 件、仅传推荐必需字段，按类型/季节预筛）、降低输出长度（`max_tokens` 收敛、理由 ≤120 字）、模型侧超时 ≤6s；失败直接返回同场景确定性兜底，不在服务端多次重试。
4. **请求合并**：切换场景/城市防抖 400ms 并取消过期请求；天气请求与本地推荐并行发起。
5. **缓存**：同一「衣橱版本 + 场景 + 天气签名」结果本地缓存 10 分钟，命中直接使用并静默刷新。
6. **可观测**：记录 `local_ready` / `ai_ready` / `ai_timeout` 耗时埋点，真机可查。

**验收标准**：

- 本地推荐首屏 ≤1s；AI 增强结果 ≤5s 到达率 ≥90%；超时率可统计且超时场景无白屏；
- 连续切换 5 次场景，实际 AI 请求次数 ≤2 次（防抖 + 取消生效）；
- 同一组合 10 分钟内重复进入命中缓存。

**涉及范围**：衣柜页推荐触发逻辑、`src/services/outfitRecommend.ts`（新增超时与取消）、`cloudfunctions/outfitRecommend`、`RecommendCard` 加载态。

### 10.4 R-4 推荐内容丰富度提升

**问题**：推荐通常仅 1–3 套、理由单行，用户感知「内容太少」。

**需求规则**：

1. **套数**：衣橱充足时默认 3 套、最多 5 套，每套带简短标题（如「稳妥保暖」「通勤利落」），标题需与实际搭配一致。
2. **每套信息**：搭配说明（温度档位 + 材质适配 + 颜色协调，≤120 字）、可选加分单品（鞋履/配饰）、注意事项（雨天带伞、风大加防风层等，按天气生成）。
3. **逐日建议**：新增「未来 3 天逐日建议」可展开区域，每天 1 套（复用明日推荐逻辑，天气取 `days[0..2]`）。
4. **衣橱利用建议**：提示本季尚未被推荐/长期未穿的单品（依赖日记-衣物关联，见 F-09；关联未落地前用「本季未推荐」近似）。
5. **缺件提示**：当前场景/天气缺失的关键品类给出参考，可一键加入试穿（备选）。
6. **文案约束**：不堆砌形容词，每条建议须可执行（含具体衣物名或品类）。

**验收标准**：

- 非空衣橱默认输出 ≥3 套（不足时说明原因，如「衣橱中仅 2 套可搭配」）；
- 每套均含搭配说明与注意事项；逐日建议可展开且与天气一致；
- 缺失品类可加入试穿；空衣橱走 9.1.2 空态引导。

**涉及范围**：`src/services/recommend.ts`、`outfitRecommend` 云函数提示词与输出契约、`RecommendCard`、试穿页。

### 10.5 R-5 云同步（含微信登录）

**目标**：换设备、多端使用时数据不丢，用户无需手动备份。

**需求规则**：

1. **登录**：`wx.login` 静默登录获取 openid，不强制手机号；未登录继续本地模式，核心功能不降级。
2. **同步范围**：衣橱（含主人信息）、衣物属性、喜爱、备注、购入信息、备选、日记、明日穿搭、出差计划；照片上传云存储并在本地保留缩略图缓存。
3. **同步策略**：本地优先（offline-first），变更先写本地再排队上行；按 `updatedAt + 版本号` 增量同步；冲突以前者时间 + 服务端版本裁决，**冲突条目不静默覆盖**，保留冲突副本供用户选择。
4. **首次登录**：检测到本地数据时提示「上传本地数据 / 使用云端数据 / 双向合并」，默认上传；选择结果记录，不重复询问。
5. **状态可视**：展示「已同步 / 同步中 / 待上传 N 条 / 失败重试」，失败可手动重试。
6. **容量**：单账号照片容量上限（免费版与会员版不同，见 R-6），超额提示清理或升级。
7. **隐私与合规**：照片与身体数据在隐私指引中声明用途；提供「删除云端数据」入口，删除后彻底清除且不可恢复。
8. **文档同步**：涉及表结构变更时同步更新 `docs/数据库开发文档` 并推送。

**验收标准**：

- 设备 A 新增衣物，设备 B 在线状态下 ≤10s 可见；
- 离线新增 10 条后恢复网络自动上行，无重复、无丢失；
- 两端同时修改同一条目时保留冲突副本，用户可选择保留版本；
- 未登录用户功能与当前版本一致；删除云端数据后服务端无残留。

**涉及范围**：新增云数据库集合与云函数（登录/同步）、`src/store`、`src/services/cloud.ts`、隐私指引、数据库开发文档。

**目标**：区分普通 / VIP / SVIP 三档会员能力，按项逐步开放，支撑可持续运营。

**能力矩阵（v1.8.1 需求方确认版，待二次确认后开发）**：

| 能力 | 普通版 | VIP | SVIP |
| --- | --- | --- | --- |

| 天气穿搭推荐 | 无 | 有 | 有 |

**需求规则**：

4. 会员状态由服务端校验，客户端不参与鉴权判断，不本地伪造。
5. 定价（月/季/年卡）、支付方式、上线节奏待用户确认；微信小程序虚拟支付与类目限制须先做合规评估（iOS 端虚拟支付受限需单独策略）。

**涉及范围**：新增会员/权益数据结构、服务端校验云函数、各受限入口的提示与跳转、支付与合规评估。

### 10.7 R-7 时尚照片集

**目标**：按衣橱主人的年龄与性别，展示当季时尚照片集（lookbook），并与「我的衣橱」做相似单品匹配。

**需求规则**：

1. **展示位置**：衣柜页/试穿页新增「当季时尚」卡片入口 + 独立照片集页（瀑布流）。
2. **筛选维度**：季节（当季）、性别（男/女/中性）、年龄段（<18 / 18–30 / 31–50 / >50）、场景（通勤 / 休闲 / 正式 / 运动）；默认按当前衣橱主人性别与年龄预选。
3. **每组内容**：封面图、标题、适用人群、3–5 套 look（照片/插画）、关键单品关键词、与本衣橱相似单品匹配数。
4. **内容来源**：首版人工维护（云数据库配置），后续可接内容平台或 AI 生成；**仅使用可商用素材，需留存版权来源**。
5. **联动**：点击 look 展示「衣橱中相似单品」（按类型/颜色/材质匹配打分）；缺失单品可加入试穿（备选）。
6. **缓存与降级**：照片集按季节本地缓存 24 小时；拉取失败展示内置默认集，不白屏。
7. 与 9.2 当季流行趋势推荐共用同一关键词库与选品匹配逻辑，避免两套标准。

**验收标准**：

- 不同性别/年龄段可看到不同照片集，默认预选与当前衣橱主人一致；
- 每季至少 6 组照片集，每组 ≥3 套 look；
- 相似单品匹配跳转正确，缺失单品可加入试穿；
- 无网络时展示缓存内容或默认集，页面无报错。

### 11.3 文档版本维护约定

2. **代码每次升版（含仅修复的 z 位递增），同步更新本 PRD**：头部「文档版本 / 日期」、追加该版本修订摘要、更新受影响需求条目、刷新第 11 章未完成项状态。
3. 某未完成项完成后：从 11.1 移入 11.2，注明实现版本与验证依据，不删除历史记录。
4. 版本递增规则以 `AGENTS.md`「版本号规则」为准：仅修复递增 z 位，新增功能递增 y 位，x 位仅在需求方明确要求时变更。
