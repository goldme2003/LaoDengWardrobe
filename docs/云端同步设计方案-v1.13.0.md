## 1. 目标

1. 换设备、多端使用时衣物、衣橱、日记、明日穿搭等数据不丢，用户无需手动备份。
2. 不改变现有「本地优先」体验：未登录、离线、同步失败时核心功能不降级。
3. 冲突不静默覆盖，用户可感知、可选择。
4. 照片随数据同步，容量按会员档位约束。

## 2. 现状与差距

| 项 | 现状 | 差距 |
| --- | --- | --- |
| 存储 | 单一本地 Storage 键 `ldw_data_v1`（[useWardrobeStore.ts](file:///g:/code_factory/AI%20Coding/Trae/LaoDengWardrobe/src/store/useWardrobeStore.ts)） | 无版本号、无脏标记、无待上行队列 |
| 登录 | 未接入 | 需 `wx.login` / 云开发 openid 静默登录 |

| 服务端 | 已有云开发环境与 members/orders 集合 | 需新增同步集合与 `userSync` 云函数 |
| 会员 | `entitlement.ts` 已登记 `cloudSync: local / cloud` | 入口、门控与容量限制未实现 |

## 3. 总体架构

```text
小程序端                                    微信云开发
┌──────────────────────────┐              ┌──────────────────────────┐
│ store (zustand)          │  dirty 标记  │ userSync 云函数           │
│   ├─ 本地 Storage 主数据 │ ───────────► │   ├─ login (openid)      │
│   ├─ sync 元数据         │              │   ├─ pull / push 快照     │
│   └─ pending 队列        │ ◄─────────── │   └─ 冲突副本写入         │
│ services/sync.ts         │              │ 云数据库                  │
│ services/cloud.ts        │              │   ├─ users               │
│ 照片：cloud.uploadFile   │              │   ├─ wardrobe_snapshots  │
└──────────────────────────┘              │   └─ sync_conflicts      │
                                          │ 云存储 user/{openid}/... │
                                          └──────────────────────────┘
```

原则：
- 本地写入永远先成功，同步是异步补偿；
- 服务端只存快照与版本，不做业务计算；
- 所有网络调用失败可重试，绝不阻塞用户操作。

## 4. 数据模型

### 4.1 集合与字段

`users`（openid 维度，1 用户 1 条）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | openid |
| `tier` | `'free'\|'vip'\|'svip'` | 服务端权威会员档位 |
| `dataVersion` | number | 云端当前数据版本号（单调递增） |
| `updatedAt` | number | 最后更新时间（epoch ms） |
| `photoBytes` | number | 已用照片容量（字节） |
| `createdAt` | number | 首次登录时间 |
| `deletedAt` | number \| null | 注销时间（宽限期 30 天） |

`wardrobe_snapshots`（每用户 1 条全量快照）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | `${openid}` |
| `dataVersion` | number | 与 users 保持一致 |
| `updatedAt` | number | 快照更新时间 |
| `data` | object | `LdwData` 全量结构（衣橱/衣物/日记/明日穿搭/自定义项/会员用量等） |

> 单用户衣物量级（≤ 500 条、照片仅存 fileID）时 JSON 约数百 KB，远低于单文档 16MB 限制；超过阈值时按实体拆表（见 4.3）。

`sync_conflicts`（冲突副本）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 自动生成 |
| `openid` | string | 用户 |
| `entity` | `'snapshot'` | 当前仅快照级 |
| `localVersion` / `remoteVersion` | number | 双方版本号 |
| `localData` / `remoteData` | object | 双方数据（仅保留差异侧） |
| `status` | `'pending'\|'resolved'` | 处理状态 |
| `createdAt` | number | 产生时间 |

`seasonal_images` / `seasonal_usage`：本期当季图组已使用，见《数据库开发文档-v0.4》。

### 4.2 云存储目录

```text
user/{openid}/items/{itemId}/{n}.jpg      衣物照片
user/{openid}/diary/{entryId}/{n}.jpg     日记照片
seasonal/{dateKey}/{season}-{gender}-{ageGroup}-{style}.jpg   当季图组（全用户共享）
```

### 4.3 扩展路径

当单用户衣物超过 500 条或快照接近 1MB 时，`wardrobe_snapshots.data` 拆为：
`wardrobe_snapshots`（衣橱）+ `wardrobe_items`（衣物，docId = openid_itemId）+ `wardrobe_aux`（其他）。同步协议不变，仅上行粒度变细。

## 5. 同步协议

### 5.1 登录

1. 小程序启动调用 `userSync` 云函数 `action:'login'`，服务端通过 `cloud.getWXContext().OPENID` 识别用户，不强制手机号。
2. 返回 `{ openid, tier, dataVersion, hasRemote, photoBytes }`。
3. 未登录 / 云环境不可用：保持纯本地，入口显示「云同步不可用」。

### 5.2 版本号与脏标记

- 本地新增 `syncMeta`：`{ openid, dataVersion, lastSyncedVersion, dirty, lastSyncedAt }`，随主文档持久化。
- 任何写操作（commit）后：`dataVersion + 1`、`dirty = true`，并写入 pending 队列（按操作类型 + 实体 id）。
- 上行成功后：`lastSyncedVersion = dataVersion`、`dirty = false`。

### 5.3 上行（push）

1. 3s 防抖聚合变更，避免频繁请求。
2. 调用 `action:'push'`，携带 `{ baseVersion, dataVersion, data }`。
3. 服务端校验：`baseVersion === users.dataVersion` → 接受，`dataVersion + 1` 落库；否则返回 `CONFLICT`。
4. 返回接受结果或冲突信息。

### 5.4 下行（pull）

- 启动、回到前台、手动下拉时调用 `action:'pull'`，返回 `{ dataVersion, data }`。
- `remote.dataVersion > local.lastSyncedVersion` 且本地 `dirty === false` → 直接覆盖本地并刷新页面。
- 本地 `dirty === true` 且远端也更新 → 进入冲突流程（6.1）。

### 5.5 状态机

```text
idle ──变更──► pending ──push 成功──► synced
                 │ 失败（网络/超时）      ▲
                 └── 重试（指数退避） ────┘
conflict ──用户选择──► pending / synced
```

## 6. 冲突处理

1. **检测**：`push` 返回 `CONFLICT` 或 `pull` 发现本地脏且远端版本更新。
2. **副本**：服务端将双方快照写入 `sync_conflicts`（`status='pending'`），不覆盖任何一方。
3. **提示**：客户端弹出「数据已在其他设备更新」：
   - 使用云端版本（覆盖本地，本地旧数据仅保留在冲突副本）；
   - 保留本地版本（强制 push，生成新版本号）；
   - 稍后处理（保持本地，状态条显示「待处理冲突」）。
4. **删除**：实体删除采用墓碑 `{ id, deletedAt }`，同步后在两端生效，避免旧设备把已删数据推回。

## 7. 照片同步

1. 首次同步：扫描衣物/日记中的本地路径，分批（每批 5 张）上传云存储，回填 `fileID` 到数据中。
2. 展示：优先使用 `fileID`（`<Image src="cloud://...">`），本地路径作为离线缓存。
3. 容量：按会员档位限制（见 8），超额时提示清理或升级，不阻断文字数据同步。
4. 失败重试：记录待上传清单，前台恢复时续传；已上传文件不重复上传（按路径 hash 去重）。

## 8. 会员与容量

| 能力 | 普通版 | VIP | SVIP |
| --- | --- | --- | --- |
| 云同步 | 无（本地） | ✓ | ✓ |
| 照片容量 | — | 500MB | 2GB |
| 冲突副本保留 | — | 30 天 | 90 天 |

- 普通版入口可见但点击提示升级（遵循 PRD 10.6 规则 1）；
- 容量值在 `entitlement.ts` 的 `cloudSync` 基础上扩展 `photoQuotaMB` 字段，服务端以 `users.photoBytes` 校验。

## 9. 安全与隐私

1. 集合权限：`users`、`wardrobe_snapshots`、`sync_conflicts` 均设为「仅管理端可读写」，客户端只能经云函数访问。
2. 云函数内按 `OPENID` 过滤，禁止跨用户读写。
3. 隐私指引声明照片、身体数据、会员信息的用途与保存期限。
4. 提供「删除云端数据」：软删除 30 天后物理删除（照片同步删除，云存储无残留）。
5. 数据传输依赖云开发 HTTPS 通道，不在客户端落任何密钥。

## 11. 里程碑与验收

### M1（首期，建议优先）
- 登录 + 全量快照上下行 + 同步状态条 + 照片上传 + 首次登录三选一。
- 验收：设备 A 新增衣物，设备 B 在线 ≤10s 可见；离线新增 10 条恢复网络自动上行，无重复无丢失。

### M2
- 增量同步（实体级）、冲突副本与用户选择、墓碑删除、断点续传。
- 验收：两端同时修改同一条目保留冲突副本，用户可选择版本；删除后另一设备不复活。

### M3
- 容量限制与清理、冲突副本过期清理、数据导出/备份（F-14）、注销宽限期。
- 验收：超容量有明确提示且不阻断文字数据；删除云端数据后服务端无残留；30 天宽限期正确执行。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 照片量大导致同步慢/费用高 | 体验与成本 | 压缩上传（≤1080px/质量 80）、分批、仅上传新增 |
| 冲突策略复杂 | 开发与验证成本 | M1 先快照级版本冲突，M2 再做实体级 |
| 多端时钟不一致 | 版本误判 | 以服务端 `dataVersion` 为唯一裁决依据，不用客户端时间 |
| 云函数/网络超时 | 假死感知 | 状态条实时反馈 + 失败重试 + 本地优先不阻塞 |
| 会员档位客户端可篡改 | 权益绕过 | 服务端以 `users.tier` 为准，客户端仅展示 |
