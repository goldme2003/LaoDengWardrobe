## 1. 目标

1. 换设备、多端使用时**衣物、衣橱、日记、自定义项、备选条目**等数据不丢，用户无需手动备份；**明日穿搭记录（勾选与推荐缓存）不纳入同步范围，仅存本地**。
2. 登录后按会员档位开通云同步，**衣橱同步数量与档位挂钩：VIP 可保存同步 2 个衣橱，SVIP 可保存同步全部衣橱**；普通版不提供云同步。
3. 同步策略为**合并优先**：登录并确认用户等级后开启同步，同步时将**云上数据与本地数据按实体合并**（而非整段覆盖），两端口径收敛一致。
4. 本地优先不改变：云同步开关关闭、离线、同步失败时，本地功能完整可用、核心体验不降级。
5. 冲突不静默覆盖，用户可感知、可选择；冲突副本统一保留 **30 天**。
6. 照片（衣物/日记照片）随数据同步，容量按会员档位约束；**明日穿搭推荐方案、当季 AI 推荐图等推荐产物仅保存在本地，不推送到云端**。

## 3. 总体架构

```text
小程序端                                    微信云开发
┌──────────────────────────┐              ┌──────────────────────────┐
│ store (zustand)          │  dirty 标记  │ userSync 云函数           │
│   ├─ 本地 Storage 主数据 │ ───────────► │   ├─ login (微信 openid) │
│   ├─ sync 元数据         │              │   ├─ pull / push 合并快照 │
│   └─ pending 队列        │ ◄─────────── │   └─ 冲突副本写入         │
│ services/sync.ts         │              │ 云数据库                  │
│   └─ 合并规则（5.5）     │              │   ├─ users               │
│ services/cloud.ts        │              │   ├─ wardrobe_snapshots  │
│ 照片：cloud.uploadFile   │              │   └─ sync_conflicts      │
│ （仅衣物/日记照片）      │              │ 云存储 user/{openid}/... │
└──────────────────────────┘              └──────────────────────────┘
```

原则：
- 本地写入永远先成功，同步是异步补偿；
- 同步范围为「所选衣橱 + 其中衣物 + 全局自定义项 + 日记 + 备选条目」；**明日穿搭记录（tomorrowOutfits 勾选 / dailyOutfits 推荐缓存）、推荐方案与 AI 推荐图不上云**；
- 服务端只存快照与版本，不做业务计算；**会员档位以服务端 `users.tier` 为准，客户端仅展示**；
- 同步采用**实体合并**，不做整段覆盖；
- 所有网络调用失败可重试，绝不阻塞用户操作。

## 4. 数据模型

### 4.1 集合与字段

`users`（微信 openid 维度，1 用户 1 条，经微信授权登录创建）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | openid |
| `tier` | `'free'\|'vip'\|'svip'` | 服务端权威会员档位 |
| `dataVersion` | number | 云端当前数据版本号（单调递增） |
| `updatedAt` | number | 最后更新时间（epoch ms） |
| `photoBytes` | number | 已用照片容量（字节） |
| `createdAt` | number | 首次登录时间 |
| `deletedAt` | number \| null | 注销时间（宽限期 30 天） |

`wardrobe_snapshots`（每用户 1 条全量快照，仅含同步范围内数据）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | `${openid}` |
| `dataVersion` | number | 与 users 保持一致 |
| `updatedAt` | number | 快照更新时间 |
| `data` | object | 同步范围数据（见 4.4）：所选衣橱 + 其中衣物、日记、自定义项（customOptions/customScenes）、喜爱品牌、备选条目、所选衣橱身体数据、编号计数器；含元数据 `syncedWardrobeIds` |
| `data.wardrobeIds` | string[] | 本快照同步的衣橱 id 集合（VIP ≤2 / SVIP 全部），两端一致口径 |

> 单用户衣物量级（≤ 500 条、照片仅存 fileID）时 JSON 约数百 KB，远低于单文档 16MB 限制；超过阈值时按实体拆表（见 4.3）。

`sync_conflicts`（冲突副本，统一保留 **30 天**，过期由云函数定期清理）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 自动生成 |
| `openid` | string | 用户 |
| `entity` | `'snapshot'` | 当前仅快照级 |
| `localVersion` / `remoteVersion` | number | 双方版本号 |
| `localData` / `remoteData` | object | 双方数据（仅保留差异侧） |
| `status` | `'pending'\|'resolved'` | 处理状态 |
| `createdAt` | number | 产生时间 |

`seasonal_images` / `seasonal_usage`：本期当季图组已使用，见《数据库开发文档-v0.4》。

### 4.2 云存储目录

```text
user/{openid}/items/{itemId}/{n}.jpg      衣物照片
user/{openid}/diary/{entryId}/{n}.jpg     日记照片
seasonal/{dateKey}/{season}-{gender}-{ageGroup}-{style}.jpg   当季图组（全用户共享，由 seasonalImages 云函数维护，与用户数据同步无关）
```

> 推荐产物（明日穿搭方案、当季 AI 推荐图）仅保存在本地缓存，不写入 `user/{openid}/` 目录、不纳入快照同步。

### 4.3 扩展路径

当单用户衣物超过 500 条或快照接近 1MB 时，`wardrobe_snapshots.data` 拆为：
`wardrobe_snapshots`（衣橱）+ `wardrobe_items`（衣物，docId = openid_itemId）+ `wardrobe_aux`（其他）。同步协议不变，仅上行粒度变细。

### 4.4 同步范围（v1.1 确定）

| 数据 | 是否同步 | 说明 |
| --- | --- | --- |
| 衣橱 `wardrobes` | ✓ 按档位上限 | VIP 最多同步 2 个、SVIP 全部；超出上限的衣橱仅本地保存 |
| 衣物 `items` | ✓ | 仅同步所选衣橱内的衣物（含照片上传） |
| 着装日记 `diaryEntries` | ✓ | 含日记照片 |
| 自定义项 `customOptions` / 自定义场景 `customScenes` / 喜爱品牌 `favoriteBrands` | ✓ | 全局共享，全量合并 |
| 备选条目（准备购入）`tryoutItems` | ✓ | |
| 身体数据 `bodyProfiles` | ✓ | 仅所选衣橱的记录 |
| 当前衣橱 `currentWardrobeId` / 编号计数器 `counters` | ✓ | currentWardrobeId 不在所选集合内时回落到所选集合第一个 |
| **明日穿搭勾选 `tomorrowOutfits`** | ✗ 仅本地 | 属「明日穿搭记录」，按需求不纳入同步 |
| **明日穿搭推荐缓存 `dailyOutfits`** | ✗ 仅本地 | 按天过期的推荐缓存，无同步价值 |
| **推荐方案与 AI 推荐图（明日穿搭方案、当季图组等）** | ✗ 不上传云端 | 仅保存在本地，不写入云存储、不纳入快照 |
| 天气城市 `city/citySource`、会员用量 `memberUsage`、临时标记 `wardrobeFilterPreset`、会员档位本地值 `memberTier` | ✗ 设备本地 | city 为设备偏好；memberTier 以服务端 `users.tier` 为准 |

## 5. 同步协议

### 5.1 登录（v1.1 确定：微信号登录 + 强制登录 + 保留开关）

1. **登录方式为微信授权登录**：小程序启动即调用 `userSync` 云函数 `action:'login'`，服务端通过 `cloud.getWXContext().OPENID` 识别微信号身份（openid 维度），全程静默无感，**不强制手机号授权**。
2. **强制登录**：微信端启动即静默登录（无弹窗、无需用户操作）；登录失败（网络异常等）自动重试（指数退避），期间保持纯本地模式，不影响任何本地功能。
3. 返回 `{ openid, tier, dataVersion, hasRemote, photoBytes, maxWardrobes, photoQuotaMB }`；`tier` 由服务端从 members 订单校验后写入 `users.tier`，客户端仅展示。
4. **云同步开关**：登录成功后云同步默认开启，用户可在「我的 → 云同步」关闭；关闭后停止 push/pull 与照片上传（登录态与本地数据保留），重新开启后恢复同步。开关状态持久化在本地。
5. 普通版（`tier === 'free'`）：登录不阻断，但云同步入口点击提示升级，不发起数据同步。

### 5.2 版本号与脏标记

- 本地新增 `syncMeta`：`{ openid, dataVersion, lastSyncedVersion, dirty, lastSyncedAt }`，随主文档持久化。
- 任何写操作（commit）后：`dataVersion + 1`、`dirty = true`，并写入 pending 队列（按操作类型 + 实体 id）。
- 上行成功后：`lastSyncedVersion = dataVersion`、`dirty = false`。

### 5.3 上行（push）

1. 3s 防抖聚合变更，避免频繁请求。
2. 调用 `action:'push'`，携带 `{ baseVersion, dataVersion, data }`（`data` 仅含 4.4 同步范围数据）。
3. 服务端校验：`baseVersion === users.dataVersion` → 接受，`dataVersion + 1` 落库；否则返回 `CONFLICT`。
4. 返回接受结果或冲突信息。

### 5.4 下行（pull，v1.1 改为合并）

- 启动、回到前台、手动下拉时调用 `action:'pull'`，返回 `{ dataVersion, data }`。
- `remote.dataVersion > local.lastSyncedVersion` 且本地 `dirty === false` → **按 5.5 合并规则将云端数据合并进本地**（新增实体直接写入、既有实体按新者胜），合并结果刷新页面；不再整段覆盖本地。
- 首次登录且云端已有数据（换设备场景）：同样执行合并——云端数据并入本地，本地独有数据保留并在合并完成后随新版本上行。
- 本地 `dirty === true` 且远端也更新 → 先执行实体级合并收敛，无法收敛的差异进入冲突流程（6.1）。

### 5.5 合并规则（v1.1 新增，同步的核心策略）

1. **实体键**：衣橱/衣物/日记/备选条目按 `id`；自定义项按 `dimension + value`；自定义场景、喜爱品牌按字符串值。
2. **合并方向**：
   - 仅本地存在 → 保留本地，随下次 push 上行；
   - 仅云端存在 → 写入本地（含照片 fileID 引用）；
   - 双方同 id → 按**最后修改时间新者胜**（实体无修改时间字段时以 `createdAt` 兜底，开发时为实体补齐 `updatedAt`）。
3. **冲突副本**：合并中被覆盖一方与生效方的差异写入 `sync_conflicts`（`status='pending'`，保留 30 天），用户可在「我的 → 冲突记录」查看，不影响使用。
4. **衣橱数量上限**：合并后若同步衣橱数超过档位上限（如降档后 VIP > 2），按「最近使用时间」保留前 N 个继续同步，超出部分转为仅本地并提示用户可在「我的 → 云同步 → 同步衣橱」手动调整；衣橱内数据不删除。
5. **合并原子性**：合并是一次本地 commit（递增 `dataVersion`、打脏标记），失败时回滚到合并前快照，保证本地数据无损。

### 5.6 状态机

```text
idle ──变更──► pending ──push 成功──► synced
                 │ 失败（网络/超时）      ▲
                 └── 重试（指数退避） ────┘
conflict ──用户选择──► pending / synced
```

## 6. 冲突处理

1. **检测**：`push` 返回 `CONFLICT`（快照版本冲突），或 5.5 合并中同 id 实体无法按时间裁决（双方同刻修改）。
2. **副本**：服务端/客户端将双方差异写入 `sync_conflicts`（`status='pending'`，**统一保留 30 天**），不覆盖任何一方。
3. **快照级冲突提示**：客户端弹出「数据已在其他设备更新」：
   - 使用云端版本（先合并云端数据到本地，差异保留在冲突副本）；
   - 保留本地版本（强制 push，生成新版本号）；
   - 稍后处理（保持本地，状态条显示「待处理冲突」）。
4. **删除**：实体删除采用墓碑 `{ id, deletedAt }`，同步后在两端生效，避免旧设备把已删数据推回。

## 7. 照片同步

1. 首次同步：扫描**衣物/日记照片**中的本地路径，分批（每批 5 张）上传云存储，回填 `fileID` 到数据中。
2. 展示：优先使用 `fileID`（`<Image src="cloud://...">`），本地路径作为离线缓存。
3. **推荐产物不上传**：明日穿搭推荐方案与当季 AI 推荐图仅存本地缓存，不调用 `uploadFile`、不占用照片容量额度。
4. 容量：按会员档位限制（见 8），超额时提示清理或升级，不阻断文字数据同步。
5. 失败重试：记录待上传清单，前台恢复时续传；已上传文件不重复上传（按路径 hash 去重）。

| --- | --- | --- | --- |
| 云同步 | 无（本地） | ✓ | ✓ |
| **可同步衣橱数** | — | **2 个** | **全部衣橱** |
| 照片容量（衣物/日记照片） | — | 500MB | 2GB |
| 冲突副本保留 | — | 30 天 | 30 天 |

- 容量值在 `entitlement.ts` 的 `cloudSync` 基础上扩展 `photoQuotaMB`（500 / 2048）与 `maxSyncWardrobes`（VIP 2 / SVIP 不限）字段，服务端以 `users.photoBytes` 与 `users.tier` 校验；
- 明日穿搭方案与 AI 推荐图为本地能力，不计入云端容量与同步范围。

## 9. 安全与隐私

1. 集合权限：`users`、`wardrobe_snapshots`、`sync_conflicts` 均设为「仅管理端可读写」，客户端只能经云函数访问。
2. 云函数内按微信授权登录所得 `OPENID` 过滤，禁止跨用户读写。
3. 明日穿搭记录与推荐方案、AI 推荐图不上云，缩小云端个人信息面。
4. 隐私指引声明照片、身体数据、会员信息的用途与保存期限。
5. 提供「删除云端数据」：软删除 30 天后物理删除（照片同步删除，云存储无残留）。
6. 数据传输依赖云开发 HTTPS 通道，不在客户端落任何密钥。

## 11. 里程碑与验收

### M1（首期，建议优先）
- 微信授权强制登录 + 云同步开关 + 同步范围裁剪（4.4）+ 全量快照上下行 + **首次/日常合并** + 同步衣橱选择（VIP 2 / SVIP 全部）+ 同步状态条 + 衣物/日记照片上传 + 冲突三选一 + **导出 JSON 兜底备份**。
- 验收：设备 A 新增衣物，设备 B 在线 ≤10s 合并可见；换设备登录后本地独有数据保留、云端数据并入（合并不丢数据）；关闭开关后不再发起任何云端请求；VIP 仅能选择 2 个衣橱同步；「我的 → 导出备份」可导出同步范围数据的 JSON 文件并通过微信分享保存。

### M2
- 增量同步（实体级）、合并差异冲突副本与用户查看、墓碑删除、断点续传。
- 验收：两端同时修改同一条目保留冲突副本（30 天），用户可查看与选择；删除后另一设备不复活。

### M3
- 容量限制与清理、冲突副本 30 天过期清理、注销宽限期（数据导出/备份已于 M1 交付；导入恢复按需另行评估）。
- 验收：超容量有明确提示且不阻断文字数据；删除云端数据后服务端无残留；30 天宽限期与副本过期正确执行。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 照片量大导致同步慢/费用高 | 体验与成本 | 压缩上传（≤1080px/质量 80）、分批、仅上传新增 |
| 合并策略误覆盖用户数据 | 数据丢失 | 仅本地/仅云端直接并入；同 id 新者胜 + 差异写冲突副本（30 天）；合并原子化、失败回滚 |
| 会员档位变更导致同步衣橱数收缩 | 超限衣橱数据「消失」错觉 | 超限衣橱转仅本地并明确提示，数据不删除，可手动调整同步集合 |
| 冲突策略复杂 | 开发与验证成本 | M1 先快照级版本冲突 + 实体新者胜合并，M2 再做冲突副本查看与实体级选择 |
| 多端时钟不一致 | 版本误判 | 以服务端 `dataVersion` 为唯一裁决依据，不用客户端时间 |
| 云函数/网络超时 | 假死感知 | 状态条实时反馈 + 失败重试 + 本地优先不阻塞 |
| 会员档位客户端可篡改 | 权益绕过 | 服务端以 `users.tier` 为准，客户端仅展示 |
