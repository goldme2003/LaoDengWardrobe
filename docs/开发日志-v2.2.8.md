## 2026-11-27 · v2.2.7（GLM模型版）

### 版本一致性校验（开发前置）

- 本地 `GLM` = `origin/GLM` = v2.2.6（已推送），工作区干净。升 `z` 位：v2.2.6 → **v2.2.7**。

### 问题（需求方 2 项）

1. 衣物详情页点「删除」没有效果；
2. 清空云端数据后再点「立即同步」，没有任何策略选项。

### 根因分析

1. **删除无效 = 云同步合并把删除的衣物复活**：`mergeSnapshot` 对衣物/日记/备选按 **并集** 合并（仅本地保留、仅云端写入）。本机删除衣物后 `dirty=true` 触发 `syncOnce`，其中**先 pull 再 push**；pull 阶段云端快照仍含该衣物 → 合并时作为「仅云端」重新写回本地，删除被撤销。同步关闭时删除本身是正常的。
2. **清空后点同步无策略选项**：v2.2.6 为避免「清空后自动恢复」，删除成功后把 `dirty` 置为 false；而 `pushSnapshot` 在 `dirty=false` 时直接返回，云端又是空的（pull 无数据）——于是「立即同步」既不弹冲突策略也不上传，表现为毫无反应。

### 改动明细

**删除墓碑（`src/store/useWardrobeStore.ts` + `src/services/sync.ts`）**

1. `LdwData` 新增 `deletedMarks`（实体 id → 删除时间戳），随本地持久化与云快照上行（仅保留 30 天内）；
2. `deleteItem` / `deleteDiaryEntry` / `deleteTryout` / `deleteWardrobe`（含其下全部实体）写墓碑；
3. `SnapshotData` 增加可选 `deletedMarks`（旧快照缺字段按空处理，向后兼容）；
4. `mergeSnapshot`：墓碑时间不早于实体最后修改时间时，跳过该实体（云端旧副本不复活、本机已删除实体不再保留）；另一端在删除后重新编辑（时间更新）则按新数据保留；墓碑按 id 取较晚时间做并集，随合并结果落地并下次上行；
5. `applyRemoteOverwrite`（云端覆盖本机）同样保留墓碑并集。

**手动同步策略（`src/services/sync.ts` `syncNow`）**

6. 云端无数据（`hasRemote=false`）、本机未打脏且本机有数据时，手动同步弹出策略选择：**「上传本机数据」**（打脏后正常上行重建云端）/「暂不上传」（云端保持为空并提示），修复「清空后点同步毫无反应」。

### 构建

- `npm run build:weapp` 通过，`npm run verify:sync` 通过；云函数未改动，无需部署。

### 版本

- `package.json` / `package-lock.json` / `APP_VERSION` → 2.2.7；日志更名 v2.2.7。

## 2026-11-27 · v2.2.6（GLM模型版）

### 版本一致性校验（开发前置）

### 问题：云同步「清空云存储数据」后云端数据自动恢复

- 现象：云同步页点「清空云存储数据」并确认后，提示清空成功，但云端快照随即又被本机数据整体写回（等同没清空）。

### 根因

1. `src/services/sync.ts` 的 `deleteCloudData` 在删除成功后被 v1.16.0 追加了 `void syncNow()`——立即以本机数据重建云端（当时为修复残留脏数据导致重复衣橱/衣物），这就是「清空后自动恢复」的**直接原因**；
2. 同一处把 `dirty` 置为 `true`：即使不立即同步，下一次回前台（`onAppShow`）/ 登录（`loginAndSync`）触发的 `syncOnce` 也会因为 `pushSnapshot` 判「有脏数据」而把本机数据重新上行，云端同样会被重建。

### 改动明细

1. `src/services/sync.ts` `deleteCloudData`：
   - 删除前先取消排队中的防抖上行（`pushTimer`），避免删除返回瞬间旧的 push 又把数据写回；
   - 删除成功后同步元数据改为 `lastSyncedVersion: 0` + **`dirty: false`** + `lastSyncedAt: 0`（不再打脏）；
   - 移除 `void syncNow()` 自动重建逻辑，云端保持空态；只有用户主动点「立即同步」或后续产生新数据变更才会重新上行。
2. `src/pages/cloud-sync/index.tsx`：清空确认弹窗文案同步改为「清空后云端保持为空，如需重新上传请点『立即同步』」。

### 说明

- 清空只影响云端快照与冲突副本，本机数据不受影响；照片文件与容量计量的清理逻辑未变。

1. **长按删除失效 + 删完回退**（`src/pages/wardrobe/index.tsx` 明日穿搭页）：

2. **多套备选重复**：
   - 今日缓存 `appendDailyOutfit` 追加时不做重复校验，AI 云函数在衣物很少时会反复挑中同一组衣物；
   - `cachedVMs` 展示层也不去重，于是出现「日常 / 旅行」两套装但衣物完全一样。

### 改动明细（均在 `src/pages/wardrobe/index.tsx`）

1. 新增套装签名工具 `outfitSig`（衣物 id 排序拼接），用于重复判定；
2. `generateOutfit`：生成前收集已有套装签名，AI 返回相同组合时改由本地规则引擎取第一套**不同**的搭配；本地也无不同组合时提示「衣橱衣物较少，暂时无法生成新的不同搭配」，且不占用当日套数；普通版同样跳过与已有套装相同的组合；
3. `cachedVMs`：按签名去重（历史重复缓存一并剔除），保留首套；

### 根因分析

1. **超时**：`provider/glmImage.js` 中单张生图硬超时 `GEN_TIMEOUT = 35000`，与日志 35134ms 吻合——是云函数自身的定时器先到，主动掐断了请求；智谱侧在 35 秒内没有返回，并非接口报错（无 HTTP 状态码）。GLM-IMAGE 为同步接口，官方文档未给出耗时承诺，第三方资料称默认档约 20 秒且随尺寸与服务端负载波动，35 秒预算偏紧。

3. **提示词**：对比后发现 v2.2.1 的 `buildPrompt` 与 `untested` 混元版逐字相同，本来就包含季节、年龄段、性别与风格，并不缺少这些维度；本次按需求进一步对齐 `outfitRecommend` 混元提示词口径，补上具体年龄与明确的穿着场景。

### 附录：小程序数据同步策略行业对比（需求方选型参考）

| 策略 | 机制 | 优点 | 缺点 | 适用场景 | 性能/成本 |
| --- | --- | --- | --- | --- | --- |
| 云端权威覆盖（cloud-wins） | 冲突时直接以云端版本为准，本地被覆盖 | 实现最简单、无弹窗打扰、逻辑可预期 | 静默丢弃本地新改动，用户无感知丢数据 | 单用户弱编辑场景（如只读配置、服务端下发的展示数据） | 最优：无合并计算，一次写入 |
| 本地权威覆盖（local-wins / last-writer-wins） | 冲突时本地全量覆盖云端 | 实现简单，用户最新操作优先 | 多端并发时互相覆盖，另一端改动丢失 | 单端强编辑、其他端极少写（如笔记单端主力） | 最优：一次写入 |
| 时间戳新者胜（LWW per-entity） | 实体按 updatedAt 逐条比较，新者覆盖旧者 | 粒度细、两端改动都尽量保留、无用户介入 | 同一实体并发编辑仍丢一侧；依赖时钟一致 | 多端同时使用的对象型数据（衣物、日记等） | 好：O(n) 合并，无弹窗 |
| 三向合并（3-way merge） | 基于共同祖先版本分别比对两端差异，字段/行级合并 | 保留两端全部非冲突改动，语义最完整 | 实现复杂，冲突字段仍需人工；需存 base 版本 | 文档/表格类高频协作（Notion、腾讯文档） | 中：计算量大，需 base 快照 |
| 冲突副本 + 用户裁决（conflict-copy + manual resolve） | 服务端保存双方副本，UI 弹窗由用户选择/对比合并 | 数据零丢失、用户可控、可追溯（副本留档） | 打断用户、交互成本高；副本需过期清理 | 低频但高价值数据（衣橱全量、订单、文档保存） | 中：多一次副本写入 + 一次弹窗 |
| CRDT（无冲突复制数据类型） | 数据结构层面保证并发合并收敛（计数器/LWW-Map/序列） | 任意并发自动收敛、离线友好 | 引入复杂库、数据模型需按 CRDT 设计、快照体积大 | 协作白板/编辑器、离线优先应用 | 前期高：库体积与学习成本；运行时好 |
| 操作变换 OT | 服务端对操作序列重排/变换后回放 | 实时协作体验佳 | 需中心服务器与操作日志，实现门槛最高 | 实时协同编辑（Google Docs 类） | 服务端重 |

- 本项目当前落地：**全量快照 + 实体级 LWW（新者胜）+ 计数器/用量取 max 的自动合并（pull 阶段）**，push 乐观锁冲突时走 **冲突副本（30 天）+ 用户三选一裁决**（v2.2.0）——属于「LWW 自动合并为主、副本兜底 + 人工裁决兜底」的混合策略，兼顾实现复杂度与数据安全；后续若引入 M2 增量同步/墓碑删除，可平滑升级为三向合并。

1. **「经常出现数据冲突」**：`pullAndMerge` 拉到云端新数据合并后，只递增本地 dataVersion 打脏，**未推进下行游标 `lastSyncedVersion`**（停在旧版本）→ 随后 `pushSnapshot` 携带过期 `baseVersion`，服务端 `baseVersion === serverVersion` 校验必不通过 → 返回 CONFLICT → 客户端「云端覆盖本地」再 force push。每次 pull 实际拉到新数据（换端启动、另一设备更新过、被踢后重新接管）都触发一次冲突链路。**修复**：合并写入后 `patchSyncMeta({ lastSyncedVersion: remoteVersion })`（不打脏），push 乐观锁随即对齐云端版本，冲突链路消除。
2. **「VIP 等级未同步」**：`userSync` login 的档位判定只查 `members` 订单集合（测试期无订单，恒为 free），未参考 `users.tier` 已登记值——另一端/上一会话经 `setTier` 写入的 vip/svip，在换设备、重装、清缓存后登录时被本地 free 上报**直接覆盖回 free**（双向互覆盖）。**修复**：login 档位判定改为三级优先：`members` 订单校验 > `users.tier` 已登记档位（不因 free 上报回退）> 客户端上报（全新用户测试期回落，支付接入后移除）。`setTier` 逻辑不变（显式变更仍实时更新 `users.tier`）。
